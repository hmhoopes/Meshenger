## Method 1: Static DH
- Uses static keys, which don't provide forward secrecy but do provide authentication / resilience to MITM
- Didn't follow this scheme since desired forward secrecy, but left as indication of thought process

### Keys
- Carry parent public key to verify parent private key
- Carry private / public key pair
    - Generated by calling `dh1(k, f)`, where `k` will contain public key and `f` will contain private key
- Both are P521

### Certifcates
- Signed by parent private key (stored in github repo, not on devices)
- Contains public key (`k`) (hashed?)

### Operation
- Scenario: User A wants to send message to User B
1. User A sends request for User B's certificate along with User A's certificate
2. User B recieves User A's request & certificate
    - User B calls `dh2(k, f)` with A's public key as first argument and B's private key `f` as second
3. User B sends response to User A containing User B's certificate
4. User A recieves User B's certificate
    - User A calls `dh2(k, f)` with B's public key as first argument and A's private key `f` as second
5. Now, User A can encrypt any traffic to B with shared secret

## Method 2: TLS-style
- **What will be used**
- Evidence that TLS does something similar:
    - https://thecybersecurityman.com/2018/04/25/https-the-tls-handshake-using-diffie-hellman-ephemeral/
    - https://security.stackexchange.com/questions/244058/explain-the-three-versions-of-diffie-hellman-used-in-ssl-tls
    - https://csrc.nist.gov/CSRC/media/Events/Key-Management-Workshop-2000/documents/tls.pdf
### Cons
- Could authenticate malicious machine if a device's private key was found
    - Permissible, as having a server's key stolen is usually "end game" for schemes
    - Could use PUF to receive temporary Certificate from parent server (see below)
- Could only use certificates for a certain period of time that must be reauthenticated
    - encryption is only between end devices, so could bring those back in to be re-authed

### Keys
- Carry parent public key to verify signatures from parent
- Carry static public/private pair purely for authentication

### Signatures
- Signed by parent private key (stored in github repo, not on devices)
- Contains public key

### Operation
- Scenario: User A wants to send message to User B
0. User A computes ephemeral DH pub/priv pair for communicating with B
1. User A sends message with:
    - Request for establishing communication
    - User A's certificate
    - A's DH pub key, signed by A
2. User B recieves User A's request
    - Computes DH pub/priv pair for communicating with A
    - Computes secret for communicating with A
3. User B replies with:
    - User B's certificate
    - B's DH pub key, signed by B
    - After sending, User B drops the pub/priv pair
4. User A recieves User B's reply
    - Computes secret for communicating with B
    - Drops pub / priv pair
5. Further communication encrypted via secret
    - Note: secret should be stored with counter of how many messages it has been sent with, after x amount it should be dropped and re-established via same method

## Method 3: Ephemeral DH w/ PUF auth
- Overview: 
    - have central server store MAC of devices with list of challenge-response pairs
        - store thousands of c-r pairs
    - Every x days, have devices re-auth to server and get new certificates
        - only use few to auth
    - have certificates for authentication that only last x days
- Would need a FPGA for this to work
